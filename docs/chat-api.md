# Customer chat API: integration guide

How a frontend (a Streamlit page, a React widget, or any other client) talks to the customer chat API: start a conversation, send messages, retry safely, read history, handle errors, and close or delete the conversation.

This guide covers the HTTP API only. The Streamlit page in [frontend/](../frontend/README.md) is a working client of it (Python, server-side). The security notes at the end matter before anything is put in front of real customers.

All paths below are relative to the API base URL, for example `http://127.0.0.1:8000`. The interactive reference is at `/docs` while `APP_ENV` is not `production`.

## The flow at a glance

```
POST   /api/v1/conversations                   -> session_id + access_token (once)
POST   /api/v1/conversations/{id}/chat         -> the reply          (Authorization: Bearer <token>)
GET    /api/v1/conversations/{id}/messages     -> the history        (Authorization: Bearer <token>)
POST   /api/v1/conversations/{id}/close        -> stop the conversation
DELETE /api/v1/conversations/{id}              -> delete it and all its messages
```

Every response has an `X-Request-ID` header. Show it (or log it on your side) when something goes wrong: it matches the server's logs.

## 1. Start a conversation

`POST /api/v1/conversations` needs no body and no token.

```json
201 Created
{
  "session_id": "3f2b8c1e-7a4d-4e9b-9c61-2d5f0a8e4b17",
  "access_token": "cst_<43 random characters>",
  "token_type": "Bearer",
  "status": "active",
  "created_at": "2026-10-15T09:30:00Z",
  "expires_at": "2026-10-15T10:30:00Z"
}
```

- `session_id` identifies the conversation. On its own it grants nothing.
- `access_token` is the conversation's secret. **It is returned only in this response** and cannot be recovered: if it is lost, start a new conversation.
- `expires_at` is when the conversation stops accepting messages (`CONVERSATION_TTL_MINUTES`, 60 by default). After that every request except `DELETE` gets `410 SESSION_EXPIRED`.

## 2. Handle the access token

Send the token on every other request, and only in the `Authorization` header:

```
Authorization: Bearer cst_...
```

- **Never put it in a URL.** URLs end up in browser history, server and proxy logs and `Referer` headers. A request with `?access_token=` or `?token=` is refused with `400`.
- **Never log it** or send it to analytics or error-reporting tools. Strip the `Authorization` header from anything you record.
- **Keep it only as long as the conversation:** in memory, or at most in `sessionStorage` for that tab. Clear it when the conversation is closed, deleted or expired.
- Anyone who has the token can read, continue, close and delete that conversation. It gives access to nothing else.

How a browser should store tokens, and how real customer identity and authentication will work, still need their own design (see [Security notes](#security-notes-for-frontends)).

## 3. Send a message

`POST /api/v1/conversations/{session_id}/chat` with a JSON body:

```json
{
  "message": "Can I return my order?",
  "client_message_id": "4c981eb1-7847-41c0-bf6b-0a0e1b9d6d91"
}
```

| Field | Required | Rules |
|-------|----------|-------|
| `message` | yes | Not blank; at most `MAX_CUSTOMER_MESSAGE_CHARACTERS` (4,000 by default) after the whitespace around it is removed. Line breaks, punctuation, emoji and any language are kept as typed. No control characters except tabs and line breaks |
| `client_message_id` | recommended | A new UUID per message, generated by the client (`crypto.randomUUID()`, `[guid]::NewGuid()`), in the standard `xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx` form. See [section 4](#4-retry-safely-with-client_message_id) |
| `category` | no | Only use FAQs in this category, e.g. `"returns"` |

Any other field (`role`, `history`, `session_id`, `access_token`, `usage`, ...) is refused with `422`. The body must be JSON (`Content-Type: application/json`).

A successful reply (`200`):

```json
{
  "session_id": "3f2b8c1e-7a4d-4e9b-9c61-2d5f0a8e4b17",
  "message_id": "b7d13f08-62ac-4f5e-a9d4-81e6c3b2f950",
  "client_message_id": "4c981eb1-7847-41c0-bf6b-0a0e1b9d6d91",
  "request_id": "6f1c0e3a9b2d4c7e8a5f1b3d2c4e6a8b",
  "decision": "answered",
  "answer": "Most unused items can be returned within 30 days of delivery. ...",
  "generation_method": "approved_faq",
  "sources": [{"faq_id": "faq_006", "question": "What is your return policy?"}],
  "usage": null,
  "created_at": "2026-10-15T09:31:06Z",
  "user_message": {"...": "deprecated"},
  "assistant_message": {"...": "deprecated"}
}
```

Use the top-level fields. `user_message` and `assistant_message` are an older shape of the same exchange, kept for compatibility and planned for removal.

`usage` is `null` when no language-model response was received (generation is off by default); otherwise it holds the reported token counts. Treat it as information, not something to bill from.

## 4. Retry safely with client_message_id

Networks fail and requests time out. Generate **one `client_message_id` per message the customer sends**, and if you have to send that message again (timeout, network error, `409`, `503`), send it **with the same ID and the same text**. The server then answers it exactly once:

| What happened to the first attempt | What the retry gets |
|-------------------------------------|---------------------|
| It was answered and stored | The same reply again: `200`, header `Idempotent-Replayed: true`, same `message_id`, `usage: null`. Nothing is answered or stored twice |
| It is still being answered | `409 REQUEST_IN_PROGRESS` with `Retry-After`: wait that many seconds and retry |
| It failed, so nothing was stored | It is answered now, once |
| (The ID was used for a different message or category) | `422 DUPLICATE_MESSAGE_CONFLICT`: a bug in the client. Use a new ID for a new message |

Rules of thumb:

- A new message from the customer means a **new** ID; a retry of the same message means the **same** ID.
- IDs only count within one conversation.
- Without an ID, a repeated request is a new message and can be answered twice.

## 5. Show the reply: answered, ambiguous, no match, unavailable

`decision` says what kind of reply `answer` is. All four are normal `200` responses: the request worked.

| `decision` | What `answer` is | `sources` | Suggested UI |
|------------|------------------|-----------|--------------|
| `answered` | An approved FAQ answer, or a checked rewrite of it | The FAQs it is based on | Show the answer; optionally list the source questions ("Based on: What is your return policy?") |
| `ambiguous` | A clarifying question | The FAQs it offers | Show the question; you may offer each `sources[].question` as a button that sends that question as the next message |
| `no_match` | A safe "I couldn't find a reliable answer, please contact support" message | Empty | Show it, plus a way to reach a person (email, phone, contact form). No ticket is created by the API |
| `retrieval_unavailable` | A "can't search right now, please try again" message | Empty | Show it and offer to try again later; a `Retry-After` header may say when |

`generation_method` says how the answer was produced: `llm_grounded` (a checked rewrite by the language model), `approved_faq` (the FAQ text word for word), `clarification` or `fallback`. Never present a `no_match` or `retrieval_unavailable` reply as an answer.

## 6. Fetch the history

`GET /api/v1/conversations/{session_id}/messages?offset=0&limit=50` (with the token) returns one page of messages, oldest first:

```json
{
  "session_id": "3f2b8c1e-...",
  "status": "active",
  "messages": [
    {"message_id": "0c9e...", "role": "user", "content": "Can I return my order?", "created_at": "...", "decision": null, "source_faq_ids": []},
    {"message_id": "b7d1...", "role": "assistant", "content": "Most unused items ...", "created_at": "...", "decision": "answered", "source_faq_ids": ["faq_006"]}
  ],
  "total_messages": 2,
  "offset": 0,
  "limit": 50,
  "has_more": false
}
```

`limit` is 1–100. While `has_more` is true, request again with `offset + limit`. Closed conversations stay readable; an expired one gives `410 SESSION_EXPIRED` (only `DELETE` still works). `GET /api/v1/conversations/{session_id}` returns just the status and timestamps.

## 7. Handle errors

Every error has the same body:

```json
{
  "error": {
    "code": "SESSION_EXPIRED",
    "message": "Your conversation has expired. Please start a new conversation.",
    "request_id": "6f1c0e3a9b2d4c7e8a5f1b3d2c4e6a8b"
  }
}
```

Branch on `code`; `message` is a short sentence you may show, but it can change. Validation errors also have `error.details`, a list of `{"loc": ["body", "message"], "type": "string_too_long", "msg": "...", "ctx": {...}}` entries (never the submitted values).

| Status | `code` | What the client should do |
|--------|--------|---------------------------|
| `400` / `422` | `VALIDATION_ERROR` | Fix the request (see `details`). For a too-long or empty message, tell the customer. Do not retry unchanged |
| `401` | `UNAUTHORIZED_SESSION` | The `Authorization` header is missing: a client bug |
| `404` | `SESSION_NOT_FOUND` | Unknown conversation or wrong token (deliberately the same). Start a new conversation |
| `409` | `SESSION_CLOSED` | The conversation is closed. Start a new one |
| `409` | `REQUEST_IN_PROGRESS` | Another message to this conversation (or this one) is being answered. Wait `Retry-After` seconds and retry with the **same** `client_message_id`. Without `Retry-After`, another message was answered at the same time: send it again (same ID is fine) |
| `410` | `SESSION_EXPIRED` | Start a new conversation |
| `413` | `PAYLOAD_TOO_LARGE` | The body is too large; the message limit is lower anyway |
| `422` | `DUPLICATE_MESSAGE_CONFLICT` | A `client_message_id` was reused for a different message: use a new ID |
| `429` | `RATE_LIMITED` | Too many requests. Wait `Retry-After` seconds |
| `503` | `SERVICE_UNAVAILABLE` | Temporary. Retry after `Retry-After` if present, otherwise after a few seconds, with the **same** `client_message_id` |
| `500` | `INTERNAL_ERROR` | Unexpected. Show a generic message with the `request_id` |

Retry only `409 REQUEST_IN_PROGRESS`, `429`, `503` and network errors, a few times, with a delay, and always with the same `client_message_id`.

## 8. Close or delete the conversation

- `POST /api/v1/conversations/{session_id}/close` stops the conversation accepting messages (`200` with its status; closing twice changes nothing). The history stays readable until the conversation expires and is cleaned up. Further messages get `409 SESSION_CLOSED`.
- `DELETE /api/v1/conversations/{session_id}` permanently deletes the conversation and all its messages (`204`). The token stops working (`404` afterwards). This also works after expiry. Offer it as "delete this conversation".

Forget the token on your side in both cases.

## PowerShell: a complete session

Windows PowerShell 5.1 or PowerShell 7, against a local server (`uvicorn app.main:app`). The token is kept in a variable and sent only as a header.

```powershell
$api = "http://127.0.0.1:8000/api/v1/conversations"

# 1. Start a conversation; keep the token out of the console and the URL.
$conversation = Invoke-RestMethod -Method Post $api
$url = "$api/$($conversation.session_id)"
$auth = @{ Authorization = "Bearer $($conversation.access_token)" }

# Send a chat message as UTF-8 JSON (Windows PowerShell 5.1 would otherwise send
# non-ASCII characters such as "é" or emoji incorrectly).
function Send-ChatMessage([string]$Text, [string]$ClientMessageId = [guid]::NewGuid().ToString()) {
    $json = @{ message = $Text; client_message_id = $ClientMessageId } | ConvertTo-Json
    $bytes = [System.Text.Encoding]::UTF8.GetBytes($json)
    Invoke-RestMethod -Method Post "$url/chat" -Headers $auth `
        -ContentType "application/json; charset=utf-8" -Body $bytes
}

# 2. Send a message and branch on the decision.
$reply = Send-ChatMessage "What is your return policy?"
switch ($reply.decision) {
    "answered"              { $reply.answer; $reply.sources | ForEach-Object { "  Source: $($_.question)" } }
    "ambiguous"             { $reply.answer; $reply.sources | ForEach-Object { "  Option: $($_.question)" } }
    "no_match"              { $reply.answer }   # offer a way to contact support
    "retrieval_unavailable" { $reply.answer }   # offer to try again later
}

# 3. A follow-up is rewritten with the conversation's context before searching. With the
#    LLM off (the default) the rule-based rewrite misses many follow-ups, so this one may
#    get the no_match message: rephrase it as a full question in that case.
(Send-ChatMessage "What about after 30 days?").answer

# 4. Retrying with the same client_message_id returns the stored reply, not a new one.
$id = [guid]::NewGuid().ToString()
$first = Send-ChatMessage "How do I reset my password?" $id
$again = Send-ChatMessage "How do I reset my password?" $id
$first.message_id -eq $again.message_id   # True

# 5. Read the history, 50 messages at a time.
$page = Invoke-RestMethod "$url/messages?offset=0&limit=50" -Headers $auth
$page.messages | Format-Table role, decision, content -Wrap

# 6. Handle an error: the body is {"error": {"code", "message", "request_id"}}.
try {
    Send-ChatMessage "   " | Out-Null   # a blank message
} catch {
    $status = [int]$_.Exception.Response.StatusCode
    $err = ($_.ErrorDetails.Message | ConvertFrom-Json).error
    "$status $($err.code): $($err.message) (request $($err.request_id))"
    # -> 422 VALIDATION_ERROR: The request is not valid. ... (request 6f1c...)
}

# 7. Close, then delete.
Invoke-RestMethod -Method Post "$url/close" -Headers $auth | Select-Object status
Invoke-RestMethod -Method Delete $url -Headers $auth
Remove-Variable conversation, auth   # forget the token
```

To read a `Retry-After` header from an error in Windows PowerShell 5.1, use `$_.Exception.Response.Headers["Retry-After"]`; in PowerShell 7, `$_.Exception.Response.Headers.RetryAfter.Delta.TotalSeconds`.

## JavaScript: sending a message with fetch()

A minimal sketch of how a future browser frontend could send one message, retrying safely. It assumes the frontend's origin is listed in `CORS_ORIGINS` (for example `["http://localhost:5173"]`) and that the token is held in memory for the current conversation only. It is an example, not a finished client.

```js
const API = "http://127.0.0.1:8000/api/v1/conversations";

// Send one customer message. The same clientMessageId is reused for every retry,
// so the server answers the message exactly once.
async function sendMessage(sessionId, accessToken, text, { attempts = 3 } = {}) {
  const clientMessageId = crypto.randomUUID(); // one per customer message
  for (let attempt = 1; attempt <= attempts; attempt++) {
    let response;
    try {
      response = await fetch(`${API}/${sessionId}/chat`, {
        method: "POST",
        headers: {
          "Content-Type": "application/json",
          Authorization: `Bearer ${accessToken}`, // header only: never in the URL
        },
        body: JSON.stringify({ message: text, client_message_id: clientMessageId }),
      });
    } catch (networkError) {
      if (attempt === attempts) throw networkError;
      await sleep(1000 * attempt);
      continue; // same clientMessageId: safe to retry
    }

    if (response.ok) return response.json(); // { decision, answer, sources, ... }

    const { error } = await response.json(); // { code, message, request_id }
    const retryable = ["REQUEST_IN_PROGRESS", "RATE_LIMITED", "SERVICE_UNAVAILABLE"];
    if (!retryable.includes(error.code) || attempt === attempts) {
      throw Object.assign(new Error(error.message), error);
    }
    const seconds = Number(response.headers.get("Retry-After")) || attempt;
    await sleep(seconds * 1000);
  }
}

const sleep = (ms) => new Promise((resolve) => setTimeout(resolve, ms));

// Usage:
// const { session_id, access_token } = await (await fetch(API, { method: "POST" })).json();
// const reply = await sendMessage(session_id, access_token, "Can I return my order?");
// if (reply.decision === "answered") showAnswer(reply.answer, reply.sources);
// else if (reply.decision === "ambiguous") showChoices(reply.answer, reply.sources);
// else showFallback(reply.answer); // no_match or retrieval_unavailable
```

A real widget also needs to handle `SESSION_EXPIRED`, `SESSION_CLOSED` and `SESSION_NOT_FOUND` by starting a new conversation, and to show `error.request_id` when it reports a problem.

## Security notes for frontends

What the API does today:

- A conversation is protected by its own random access token, checked on every request; a wrong token and an unknown conversation look the same (`404`).
- Tokens are never logged by the server, are stored only as a hash, and are refused in URLs.
- CORS is closed by default and lists exact origins only. **CORS is not authentication**: it only controls which web pages may read responses in a browser. Any other client can still call the API, so every request is authorised by its token, not by its origin.
- Request-rate limits exist but are **process-local and in memory** (reset on restart, separate per worker): a prototype safeguard, not protection for a public deployment.

What still needs its own design before real customers use a frontend (planned for Stage 9):

- **Browser token storage.** Memory or `sessionStorage` for one conversation is the simplest acceptable choice for a demo. `localStorage` survives the tab and is readable by any script on the page, so a cross-site-scripting bug would expose tokens. An `HttpOnly` cookie set by a backend-for-frontend would be safer, but needs CSRF protection and a different CORS setup. This decision belongs to the frontend design, together with a Content Security Policy.
- **Who may use the API at all.** There are no API keys or accounts yet: anyone who can reach the server can start conversations and use the FAQ and answer endpoints. Production needs authentication for each client site (and possibly for customers), durable rate limiting and quotas at the deployment, and HTTPS.
- **Privacy.** What customers type is stored in the conversation until it is deleted or expires, and is sent to OpenAI when generation is enabled. A real deployment needs a privacy notice and a review for its jurisdiction.
